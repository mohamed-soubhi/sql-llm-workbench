01 What it is

One HTML file that turns five HR CSVs into a queryable SQLite database inside your browser, then lets you query it two ways: in plain English (translated to SQL by a local model) or by writing SQL yourself.

The whole idea
There is no backend. The database engine, the data, the UI, and the SQL all live in the page. The only outside calls are the sql.js library (CDN) and — for the English mode only — your local Ollama server.

02 Architecture

Layers, bottom-up

  1. Data layer — the 5 CSVs + the CREATE TABLE DDL, embedded as JS strings. No file reads at runtime.
  2. Engine layer — sql.js (SQLite/WASM). One in-memory database, built once at load.
  3. Logic layer — CSV parsing, query execution, result shaping, and (for Ask) prompt building + SQL extraction + a read-only guard.
  4. UI layer — tabs, chat stream, SQL editor, schema rail, result table.

04 Boot workflow

Runs once, when the page opens. Ends with the status chip reading ok · 5 tables · 36 rows.

  1. Page parses; the browser fetches sql-wasm.js from the CDN and its .wasm companion.
  2. initSqlJs() resolves; boot() creates an empty in-memory database.
  3. DDL runs → the 5 tables exist (empty).
  4. For each table in _order: parseCSV() splits the embedded text into rows, then a prepared INSERT writes them with the fixed column list.
  5. Row counts are stored in DB_INFO; renderSchema() draws the rail; the status chip updates.
If boot fails
The chip turns red and the schema rail shows the error. Almost always a blocked CDN — the engine could not download. Check network / CDN access.

05 Ask workflow (English → SQL)

  1. You type a question and press Enter (onAsk).
  2. Your question is echoed into the chat; a “thinking…” bubble appears.
  3. askLLM POSTs to http://localhost:11434/v1/chat/completions with a system prompt = the DDL + a column glossary + few-shot examples + the rule “output only one SELECT”.
  4. The reply is passed to extractSQL, which strips fences/prose and keeps the SELECT.
  5. isReadOnly checks it: must start with SELECT/WITH/EXPLAIN and contain no destructive keyword.
  6. The SQL is shown in a copyable block, then executed via runSql; the result grid fills below.
Why the model sees the schema
The prompt embeds the exact table/column names and the join keys, so the model names things correctly instead of guessing. That glossary is what makes joins like EMPLOYEES.DEP_ID = DEPARTMENTS.DEPT_ID_DEP work.
Ollama must be reachable from the browser
Browsers block cross-origin calls by default. Start Ollama with OLLAMA_ORIGINS='*', or serve the page from http://localhost. On failure the page prints both fixes and Direct mode keeps working.

06 Direct SQL workflow

  1. Switch to Write SQL (or click a column in the schema rail to jump there).
  2. Type SQL in the editor. Ctrl/Cmd+Enter or Run query.
  3. The statement executes against the same in-memory engine — no model, no network.
  4. Results render as a grid; multiple statements return the last result set.

Direct mode is the fallback: it works with no Ollama, no keys, no server — just open the file.

Dates & types
Dates are stored as YYYY-MM-DD text; SQLite compares them as strings, which sorts correctly. Column types come from your DDL but SQLite is dynamically typed, so no coercion runs on insert.

10 Limits & gotchas

  • In-memory only. Reload resets to the original CSVs. Nothing is saved back to your files.
  • Read-only for Ask. Generated DML/DDL is refused by design. Direct mode allows writes, but they vanish on reload.
  • Ollama origin. Ask mode needs OLLAMA_ORIGINS='*' or a served page. Direct mode never needs it.
  • CDN dependency at load. No sql.js download → no database. Cache it locally if you need fully offline runs.
  • Headerless CSVs. If you replace a CSV, column order must match the cols array exactly.
  • Extraction is heuristic. If the model wraps SQL in prose the parser still finds it, but a model that emits two statements may confuse the guard.
